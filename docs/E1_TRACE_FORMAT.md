# E1 trace format (MAME reference for the Hyperstone CPU)

Generated by `python scripts/mame_e1_trace.py <set> <N>` (`scripts/mame/e1trace.lua`, converted by
`scripts/e1trace_convert.py`). Outputs in `sim/ref/<set>/` (`*.trace` is gitignored; samples in
`sim/ref/sample/` are committed).

## What is traced

- **Interpreter traces.** MAME runs with `-debug -nodrc`: the E1 core runs through
  `hyperstone_device::execute_run` (`e132xs.cpp`, `e132xsop.hxx`), not the DRC recompiler. The
  per-instruction record comes from the debugger's `trace` command, which fires at
  `debugger_instruction_hook(PC)`, **before** the instruction executes.
- Binary 0.289 (`mame.exe -version`); source tree differences: `docs/HARDWARE_NOTES.md`, "MAME version".
- Starts at the reset: instruction 0 is at the reset PC. MAME does not read a vector; it sets
  PC = trap_entry + TRAPNO_RESET*4 with trap_entry = 0xffffff00 (MEM3): PC = 0xfffffff8
  (`device_reset`, `get_trap_addr`, `e1defs.h` TRAPNO_RESET = 62).
- NVRAM is empty (scratch directory), so the EEPROM starts blank, as in `mame_boot_trace.py`.

## `<set>_instr.trace`

Text, one record per instruction, in execution order. `#` lines are comments.

```
idx pc ops sr changes | disasm
```

| Field | Meaning |
|---|---|
| `idx` | 0-based instruction index |
| `pc` | address of the instruction (= g0 as the interpreter holds it before the fetch), hex |
| `ops` | opcode halfwords actually fetched, comma separated (1 to 3). Length is taken from the bus fetches of that instruction |
| `sr` | g1 before the instruction, hex |
| `changes` | registers whose value differs from the previous record's pre-state: `gN=hex` (N = 2..31) and `lN=hex` (N = 0..63, the raw local array `local_regs[N]`, **not** FP-relative; MAME names these `S<N>`). Record 0 lists every register (full state) |
| `disasm` | MAME's disassembly, `ADDR: text` |

Reconstructing the full pre-state of record k: start from record 0 and apply the `changes` of records
1..k. g0 is `pc` and g1 is `sr`. Global names in the E1: g2 FER, g18 SP, g19 UB, g20 BCR, g21 TPR,
g22 TCR, g23 TR, g24 WCR, g25 ISR, g26 FCR, g27 MCR. g23 (TR, the timer) is the array element as the
interpreter holds it; it is not recomputed per instruction.

`# frame F starts before idx I`: the MAME frame notifier for frame F fired between instruction I-1 and I
(the end of frame F, so the first marker, F=0, is the end of frame 0).

Not exposed: `delay_slot`, `delay_pc`, `delay_slot_taken`, `intblock`, `trap_entry`, `timer_int_pending`,
the interrupt-line state. They are not device-state entries (`e132xs.cpp` `device_start`, `state_add`),
and the debugger and Lua read only state entries. Delay slots are visible in the stream (the instruction
after a `.D` branch/load is the slot, executed before the target). An interrupt taken shows as `pc`
jumping to the trap table (0xffffff00 + 4 * trapno; INT1 = trapno 53 = 0xffffffd4) with `ISR`
(g25) visible before and after. The smallest source patch to expose the rest is one `state_add` per
field in `hyperstone_device::device_start` next to the others (`delay_slot`, `delay_pc`,
`delay_slot_taken`, `intblock`, and the interrupt input state); not done, no local build.

## `<set>_bus.trace`

```
idx kind space addr data mask
```

One row per access the CPU made while executing instruction `idx`, in order. Rows come from
memory taps, so they are what MAME's address spaces saw, one row per bus transfer (a 32-bit access
on the 16-bit bus is two rows).

| Field | Meaning |
|---|---|
| `kind` | `F` instruction fetch, `R` data read, `W` write |
| `space` | `P` program, `I` I/O |
| `addr` | program space: byte address, hex. I/O space: the driver's address (word units; `0x0f0` is the EEPROM write in `misncrft_io`) |
| `data` | 16-bit data, hex (the read value, or the value written) |
| `mask` | lanes driven: `ffff`, `ff00` or `00ff` |

`F` is assigned in the converter: a program read with mask `ffff` at `pc`, `pc+2`, `pc+4` in sequence
at the start of the instruction's rows. A data read that happens to hit those addresses first would
be mislabelled; none was seen.

### 32-bit bus rows (E1-32, `bus_bytes` 4 in `scripts/mame/regions.json` "sets")

Selected per set by `regions(game)` (`wivernwg`: `common_32bit_map`, `wyvernwg_io`). The Lua taps log the
raw 32-bit `data` and `mask` of the tap; the converter writes 8-digit hex fields:

| Field | 32-bit meaning |
|---|---|
| `addr` | program space: byte address of the first lane driven (the tap's offset is the dword address; the lane comes from the mask). I/O space: the tap's offset |
| `data` | the lanes driven, in place (`data & mask`, not shifted): a halfword at `addr` with bit 1 clear is `xxxx0000` |
| `mask` | lanes driven: `ffffffff` (dword), `ffff0000` / `0000ffff` (halfword), `ff000000`, `00ff0000`, `0000ff00`, `000000ff` (byte) |

A dword access is one row. Instruction fetch stays one halfword per `F` row (`e132xs.cpp` fetches through
`m_pr16`, a 16-bit read on the 32-bit cache): `F` is a read with the halfword lane mask at `pc`, `pc+2`,
`pc+4`. I/O rows are always `ffffffff` with `addr` the driver's address (`0x1f00` is `eeprom_r` in `wyvernwg_io`):
`m_read_io` is `read_dword(address >> 13)`, and a handler with `umask32` shows no narrowing in the row. The 16-bit format above is unchanged (4-digit fields).

`wivernwg` relocates the trap table to MEM0 (TPR), so interrupt entries are `(63 - trapno) * 4` (INT2 = `0x2c`,
timer = `0x20`), not `0xffffff00 + 4 * trapno`. A `MOV Ln, TR` row's value is MAME's cycle-count timer
(`compute_tr`) and is not reproducible by the RTL; `sim/e1_tb` takes it from the trace.

Artefacts removed or kept:

- MAME reads the first instruction once before execution starts (`execute_run` computes the
  instruction length); that single read at 0xfffffff8 is dropped.
- Taps also fire for the debugger's own reads (disassembly, `w@pc`); the Lua script ignores accesses made
  with side effects disabled.
- `speedup_16_r` handlers on idle loops (`init_misncrft`, 0x741e8 and 0x72e2c in work RAM) call
  `spin_until_interrupt` / `eat_cycles` when PC is 0xff5a / 0xecd6. They do not change the
  instruction or bus stream but make later frames execute far fewer instructions than real hardware
  would. Timing in these traces is not hardware timing.

## `<set>_frames.txt` (`--lean`)

`frame instructions` pairs from a PC-only run (`--lean --frames F`): instructions executed in
each frame.

## Frame dumps

`scripts/mame_capture.py misncrft --frame F --out <abs path>` (run with `-nodrc`) writes
`workram.bin` (0x00000000-0x001fffff), `spriteram.bin` (0x40000000-0x4003ffff), `palette.bin`
(0x80000000-0x8000ffff), all read through the CPU's program space (big-endian bytes), and
`reference.png` (MAME's native snapshot, 320x236, the game's rotation not applied).
Use an absolute `--out`: MAME runs in its own directory.
