--- reading ---
Sprite RAM
- Written once per frame, in one ascending pass from 0x40000000 to 0x40007ffe (misncrft, 16384 16-bit writes
  = bands 0..15) or to 0x4000800c (wivernwg, 8196 32-bit writes = bands 0..15 plus the first 16 bytes of
  band 16). 0 writes out of order in 300 frames. The pass starts on line 252 and ends on line 259 in all 300
  frames of the order run and in 1800 of 1800 frames of three of the four 1800-frame runs ("last" rows:
  line 259). The exception is wivernwg attract: 1758 of 1800 frames have the pass (8004.8 writes per frame,
  not 8196); the other 42 frames have no sprite RAM write at all (cause not looked into). No write to
  0x40008800 and up (spr_rest empty).
- Band 0 is written but draw_sprites never reads it (unflipped: strips y/16 = 1..15, bands 15..1; flipped:
  bands 1..15). spr_used (the bytes that are read): 15360 words per frame, same line range.
- No write in active display (lines 16..251): 0 of 29,491,200 (misncrft) and 14,408,568 (wivernwg) writes.
- Attract and play do not differ: same counts per frame, same lines. (Contents differ; timing does not.)
Palette
- 236.4 (attract) / 331.0 (play) 16-bit writes per frame on misncrft, 48.0 / 33.0 32-bit writes on wivernwg.
  Lines 259..263 and, on wivernwg attract, 0..2 (5.5% of writes). 0 writes in lines 16..251. Right after
  the sprite pass: the palette is written in some frames only (misncrft attract 1004 of 1800 frames,
  wivernwg attract 384), and the last palette write of such a frame is on line 259 or 260 in all but 3
  (misncrft attract: one on 263; wivernwg attract: two on line 2).
Flip
- io_flip: 0 writes in 3600 counted frames per set. The game writes the flip port once at boot, value 0
  (vcap manifests: "flip_writes 1 first 3:0" misncrft, "1:0" wivernwg, through frame 5600). Flip is a
  constant for these games.
When MAME reads sprite RAM
- vamphalf.cpp sets no VIDEO_UPDATE_AFTER_VBLANK, so screen_device::vblank_begin (emu/screen.cpp:1149) calls
  screen_update at vblank start, before the vblank callbacks that raise the E1's IRQ1. The picture of a
  frame is therefore the sprite RAM and palette as they stand at the start of line 252: the list written
  by the pass of the previous vblank, complete (that pass ended on line 259 of the field before).
- The Lua frame notifier runs in the same vblank_begin; RAM dumped there is the RAM the picture was drawn
  from (342 of 342 frames per set pixel-identical, moving sprites included: docs/MAME_KLUDGES.md, Video).
  Contrast with a driver that sets VIDEO_UPDATE_AFTER_VBLANK, where the notifier is a frame later.
- Evidence of what the real board does: none beyond one driver comment (vamphalf.cpp:44-49): the Semicom
  boards never output 4 lines, confirmed on hardware. Nothing about when sprite RAM is read or written. The
  burst length is MAME's: 16384 16-bit writes in about 8 lines is about 1.6 CPU clocks per write at 50 MHz,
  from MAME's instruction timing, which the driver calls "probably incorrect" (vamphalf.cpp:1143). Unverified
  for the board and unverified for the RTL CPU (CPI 2.71 at zero wait).
What it means for the sprite-list latch (references/video_write_sweep.md section 5, step 7 and 8)
- Row "list written entirely inside vblank, before line X": snapshot at line X or later, before active
  video. In MAME's timing X = 260; the first line that is read is 16, so 252..263 plus 0..15 leaves a
  window of lines 260..15 (20 lines, 8960 pixel clocks, 71,680 clk_sys cycles at 56 MHz) between the end of
  the pass and the first sprite line.
- Because the pass is a single ascending run that ends with the write to 0x40007ffe (misncrft) /
  0x4000800c (wivernwg), "done" can be taken from that write instead of a fixed line; a fixed line chosen
  from MAME's timing is the fallback and holds only if the RTL pass is not longer than the window.
- MAME's equivalent latch point is line 252, before the pass starts. A latch at line 252 would have to copy
  or hold the list while the CPU starts rewriting it (race, LESSONS_LEARNED "A snapshot is a race with
  whoever writes the thing being copied"). A latch after the pass has the same content (no writes in lines
  260..251) and no race.
- Reading live during active display gives MAME's picture for these two sets (no active-display writes).
  It is not safe if the RTL CPU's pass runs into line 16.
- The RTL's pass duration is the number to measure before choosing: it decides between fixed line, done
  write, and a double-buffered list.
