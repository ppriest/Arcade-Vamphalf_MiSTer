# QS1000 trace format (MAME reference for the sound CPU's 8052)

Generated by `python scripts/mame_qs1000_trace.py <set> <N>` (`scripts/mame/qs1000trace.lua`). Sets:
`misncrft`, `wivernwg` (and their clones). Output in `debug/qs1000/` (a junction to D:; the files are
large, about 100 bytes per instruction). Samples of the first 2000 instructions are in
`sim/ref/sample/qs1000_misncrft_*_first2000.txt`. Consumed by `sim/qs1000_tb` (`run_verilator.sh qs1000_tb`).

## What is traced

- Device `:qs1000:cpu`, an `i8052` at 24 MHz (`qs1000.cpp`, external program ROM `u7`). MAME runs
  with `-debug`; the per-instruction record comes from the debugger's `trace` command with an action
  (`tracelog`), which fires at `debugger_instruction_hook(PC)`, before the instruction executes.
  The 8052 core is an interpreter; the main CPU runs under the DRC.
- Starts at the reset: instruction 0 is `ljmp 0024` at 0x0000. Internal RAM is not dumped; the 25
  reads of never-written locations at or above 0x20 in `misncrft` all return 0.
- The script sets `debugger.visible_cpu` to the 8052. `tracelog` writes to the visible CPU's trace
  file, so without it the rows of every tap would be lost. (`focus` does not set it.)
- Debugger expression arguments are printed with `0x`: a bare `a` or `b` is the ACC or B symbol
  and evaluates to a register, not the number (an offset of 0x0a was logged as 0 before this).
- The run stops when the log holds more than N instructions; the converter trims to exactly N.

## `<set>_instr.trace`

```
idx pc a psw sp dptr r0 r1 r2 r3 r4 r5 r6 r7 b ie ip tcon tmod tl0 th0 tl1 th1 | disasm
```

All fields hex, state **before** instruction `idx`. `r0..r7` are the registers of the bank selected
by PSW. `disasm` is MAME's `ADDR: text`. Interrupts have no record of their own: an interrupt taken
shows as `pc` = the vector (0x0b, 0x13, ...) with `sp` two higher and the pushes in the bus rows of
the previous instruction.

## `<set>_bus.trace`

```
idx space kind addr data
```

`idx` is the instruction executing, except for `L`. Rows are in the order MAME's address spaces saw
them (memory taps).

| space | Meaning |
|---|---|
| `I` | internal RAM (`idata` space): direct accesses below 0x80, indirect `@R0/@R1`, stack pushes and pops, interrupt pushes. `addr` 00-ff, 8 bit data |
| `S` | SFR (`sfr` space): direct and bit accesses. `addr` 80-ff. Port rows are the values the port callbacks returned (reads) or the new latch (writes) |
| `X` | external data (`xdata`): `MOVX`. 16-bit address; `@Ri` forms carry P2 in the high byte |
| `P` | program-space reads that are not the instruction's own fetch: `MOVC` |
| `L` | the main CPU's write to the sound latch (I/O offset in `addr`, byte in `data`); `idx` is the instruction whose record precedes the write |

`kind` is `R` or `W` (`W` for `L`). The instruction's own fetch rows (opcode and operands at
`pc`...) are removed by the converter, using an opcode length table; a fetch after an interrupt
entry reports address 0000 for its first row (the data byte is correct), which the converter accepts.

## What MAME exposes

- Per instruction, as debugger state: PC, SP, PSW, A, B, DPTR, IE, IP, P0-P3 (read with side effects
  off), R0-R7, RB, TCON, TMOD, TL0, TH0, TL1, TH1. The 8052 adds no state entries: **T2CON, T2MOD,
  RCAP2, TL2/TH2, SCON, SBUF and PCON are not readable as state**.
- Every access to the four address spaces `program`, `xdata`, `sfr`, `idata` through taps, with the
  value. This includes all SFR accesses (so every Timer 2 SFR access would be logged) and every
  indirect access to internal RAM at 0x80-0xff.
- The main CPU's sound-latch write through a tap on its I/O space.

## What MAME does not expose

- Register-bank accesses (`Rn`): the core reads and writes its RAM array directly. The registers
  are in the instruction record instead; the bench merges them into its RAM image.
- Initial RAM contents (assumed zero), cycle counts and time stamps (MAME's `icount` is not
  reachable; instruction order only), timer overflow and serial events, the INT1 pin level
  (rebuilt from the `L` rows and the acknowledge: a P3 write with bit 5 low, `qs1000_p3_w`),
  interrupt-in-service state, the `m_rwm` flag. Reads of a port by a read-modify-write instruction
  return the latch (as the core does), the same row type as a pin read.
- The INT1 assertion time. `L` rows are the main CPU's writes; the latch device raises the pending
  line from a scheduler time-sync callback some time later (the first `L` of `misncrft` precedes
  the INT1 vector entry by 1,719 instructions). What the trace shows is the instruction where the
  interrupt was taken: `pc` = 0x13 with `sp` two higher.
- Port reads: P1 reads return the sound latch. Every P3 read in the 3,000,000-instruction traces is
  a read-modify-write (the latch value, `P3 R` count = `P3 W` count); no P0 or P2 read occurs. A
  pin read of P3 would go through the unconfigured `p3_in` callback of `qs1000.cpp` (default 0);
  this is untested.
- Wavetable output is not traced (`X W` to 0x200-0x211 is).

## Notes

- A tap's `offset` for the first fetch row of an instruction reached through an interrupt is 0000.
- The hardware pushes of an interrupt entry are logged after the previous instruction's rows and
  tagged with its index; the vector instruction's own record follows.
- Counts and what they show: `docs/QS1000_8052_FINDINGS.md`.
